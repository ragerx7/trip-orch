Trip Orchestrator — Reference for Product & Engineering Leadership

The Trip Orchestrator

This is the complete definition of the reasoning system, not the pitch for it — the loop that runs it, the memory and components it runs on, and what each component actually does internally, step by step. It has been stress-tested against edge cases and rehearsed in a working simulation; both are referenced at the end. What follows assumes the problem statement is already agreed, and spends its length on the mechanism instead.

"Given the traveller's objectives, current trip state, external events, existing commitments, constraints, preferences, and available capabilities — what should happen next?"

The one question the system answers, asked continuously from discovery to trip completion. Everything below is how.

01

Three pillars

The architecture rests on two distinct representations, coordinated by the orchestrator rather than owned by either one alone.

Trip Graph — the traveller's journey
  1. Flight
  2. Airport Transfer
  3. Hotel
  4. Activity
  5. Train
  6. Hotel
  7. Return Flight
Task Graph — the orchestrator's work
  1. Understand Intent
  2. Identify Missing Information
  3. Construct Trip
  4. Validate Trip
  5. Search Options
  6. Obtain Approval
  7. Book Components
  8. Prepare Traveller
  9. Monitor Trip
  10. Handle Disruptions

The Trip Graph holds destinations, transport, accommodation, activities, timing, dependencies, and commitments — what should happen to the traveller. The Task Graph holds every unit of work needed to make that happen — what the orchestrator does, not what the traveller experiences. The distinction is fundamental: one describes the journey, the other describes the work. The orchestrator's whole job is coordinating both.

Three different kinds of thing make that coordination possible — Reasoning, Memory, Tools — and the boundary between them is the one rule that keeps the system legible as it grows. What they add up to is a loop, covered next (§02).

Reasoning

Judgment, held nowhere

Reconciler · Classifier · Prioritizer · Autonomy gate · Dispatch · Clarification

Carries no state between cycles. Everything it needs, it reads fresh.

Memory

What persists

Desired state · Actual state · Commitment state · Task graph · Decision log · Traveller preferences

Inert. It answers questions; it never asks one.

Tools

Stateless executors

Planning · Sourcing & Booking · Pre-Trip Prep · Monitoring · Post-Trip

One slice each, a fixed function set, never calls another tool.

Reasoning's separation of concern: the only place judgment happens. It never touches a supplier, a document, or a booking system directly — its job is to decide, using what Memory holds and what a Tool reports back.

PartWhat it doesExample
ReconcilerDiffs Desired against Actual against Commitment for the affected Trip Graph node, then walks outward along its edges to see how far the divergence reaches — the single, bounded scope everything downstream reacts to.Flight now lands 6:15pm, not 3:15pm → diffed against Commitment's 3:30pm transfer, then walked along the edge toward Day 2's cruise. Output: a bounded scope, not just "the flight is late."
ClassifierSorts a divergence into exactly one category, which alone decides what happens next: absorbable (slack covers it), correctable (a fix restores the shape), structural (the shape itself no longer fits).3h delay with slack = absorbable. Same delay hitting a paid cruise = correctable (Planning rebooks, shape holds). 8h delay costing the connecting flight = structural (Planning must pick a different shape).
PrioritizerGate-then-score across every open task — hard disqualifiers first, then a weighted score on survivors. Never one multiplicative formula."Confirm the cruise" gates in as urgent (real money, real deadline); "suggest a cooking class" is scored, not gated — it can wait a day without being dropped.
Autonomy gateSets the tier — Inform, Recommend, Confirm, Auto, Escalate — from irreversibility and financial exposure (§03).Moving a free, refundable transfer = Auto. Rebooking a non-refundable cruise for +₹1,200 = Confirm.
DispatchTakes a Task Graph node and routes it to the component that acts on the Trip Graph nodes it touches. Doesn't do the work, only routes it.A revised-schedule need routes to Planning; securing a specific flight routes to Sourcing & Booking.
ClarificationA component hands back a question instead of a result; only the core decides how to resolve it — memory, benchmark data, the traveller, or another component. The asker never learns which.Missing origin city → ask the traveller. Missing passport expiry → ask the traveller. Missing flight cost → ask Sourcing & Booking (§05, §07). Same mechanism, three resolutions.

Memory's separation of concern: total, from Reasoning. Memory holds facts; Reasoning holds judgment about them. It never initiates anything.

Concretely, in Memory: a Trip Graph node carries its Desired, Actual, and Commitment attributes together, connected by edges recording what depends on what. A Task Graph node references which Trip Graph node(s) it touches — narrow, broad, or propagating, below.

StoreWhat it holdsExample
Desired stateWhat the traveller wants — objectives, preferences, constraints.Vietnam · 7 days · ₹2,00,000 total · 2 travellers · October — written the instant intent is stated.
Actual stateWhat's actually true right now, at whatever confidence the last read allows.AI 2436 — landing 6:15pm (was 3:15pm) — confirmed 4 min ago. The timestamp is what lets the Reconciler judge staleness, not just status.
Commitment stateWhat's locked in for a node — booked, paid, at what cancellation cost — plus its position in the sequence: what it follows.Ha Long cruise — ₹8,500pp — non-refundable — Day 2, 1pm — follows: Day 1 transfer + hotel check-in. The cancellation cost is what's at stake if the edge below runs out of slack.
EdgesThe dependencies between Trip Graph nodes — what a divergence in one node can reach, and how far. Built by Planning (§05, Step 8) when the days are sequenced, not inferred after the fact.Flight → Transfer (zero slack, always retimed) → Day 2 cruise (slack: ~14h). A 3h delay never reaches the cruise edge; an 8h one does.
Task graphEvery unit of work, referencing which Trip Graph node(s) it touches — narrow (one node), broad (the whole graph), or propagating (walks outward along edges from one node).SEARCH_OPTIONS: narrow, touches one Flight node. VALIDATE_TRIP: broad, spans the whole graph. HANDLE_DISRUPTIONS: propagating, walks from Flight outward until slack absorbs it.
Decision logWhy a past action was taken — makes "verify outcome" mean something.transfer moved to 9:15pm — reason: AI 2436 delayed 3h, absorbable, Auto tier.
Traveller preferencesThe one store that outlives this trip.kept: cruise, lantern class · skipped: night market — read by Planning before a single new preference is asked for again.

Tools' separation of concern: narrower than either of the other two. One bounded thing each, a fixed function set, and never a decision on whether it should run — that's Dispatch's call, always. Full depth for each is in §05–09.

ToolWhat it doesNote
Planning →§05Turns an envelope into a trip structure.Destination, coverage, routing, days — never touches a supplier.
Sourcing & Booking →§06Turns one specific need into a secured commitment.This flight, this hotel — gated then scored on what's scarce for this trip.
Pre-Trip Prep →§07Confirms fitness to depart.Visa rules, passport validity — a hard blocker escalates immediately.
Monitoring →§08Watches, continuously, without being asked.The only tool subscribed to, not dispatched to (§04).
Post-Trip →§09Closes the loop.Reconciles spend, writes what to keep in Traveller preferences.
02

The reasoning loop

The central question isn't answered by a pipeline that runs once per trip. It's a cycle the orchestrator re-enters every time something changes — a new input, a supplier event, a clock tick, a finished task. Most passes through the cycle end almost immediately: nothing has actually diverged, so nothing happens. The two branches below are where that changes — where a real divergence is found, and where the traveller has to be the one who decides.

On concurrency: this diagram draws one trigger's journey — it isn't a claim that only one is ever in flight. A delay and a passport flag can arrive seconds apart, and each gets its own pass through Reconcile → Classify → Dispatch. Memory, not the loop, prevents them from racing: writes to a trip's state are serialized, so the second trigger's Reconcile always reads what the first already wrote. Two different trips never contend at all — they don't share state.

On how a trigger is detected: one node, four different mechanisms.

SourceHow it's detected
Traveller inputArrives through the Interface layer already a trigger. A receipt, not a detection.
Component responseDispatch hands work to a component; its return (a result or a question) is the next trigger — a continuation of the call, not a separately-watched event.
Supplier / MonitoringThe one continuous watch, detailed in §08: a live feed or poll, diffed against last-known status, pushed the moment it changes.
Clock tickThe one source with no push of its own. A scheduler outside the loop polls Memory for deadline-shaped questions — has a Confirm request passed its deadline (§03), has the last anchor event's time passed (§09) — and enqueues a trigger the moment the answer flips to yes.
03

Talking to the traveller

There's no separate notification system bolted on the side. The autonomy gate is the only place the loop decides to involve a person, and the tier it picks is the message. A traveller's response is not a special input — it re-enters the loop at the top, as an ordinary trigger, same as a flight-status webhook.

TierMeaningWaits?
InformTold, not asked. No exposure, fully reversible.No
RecommendSuggested; the default runs if ignored.No
ConfirmWaits on a yes — real money or a real commitment at stake.Yes
AutoActs immediately. Reversible, zero or near-zero cost.No
EscalateStructural break, or a call the system shouldn't make alone.Yes

On silence: an unanswered Confirm or Escalate is the normal case for anyone who doesn't check their phone for a day. The default is never to act on silence: an unanswered Confirm expires at the underlying task's own deadline (a booking hold's real cutoff, not an arbitrary clock), re-notifies once as that nears, and — if it still passes — marks the task expired in the Task graph and surfaces the consequence plainly, rather than silently retrying or proceeding. Escalate behaves the same way but doesn't default to inaction indefinitely: past its deadline it hands off to human support, the same off-ramp §12 reserves for long-tail failures this system was never meant to resolve alone.

04

The system, stitched together

One structural view: the reasoning core sits between the traveller and everything else, reads and writes one shared memory, and dispatches to the same four invoked components regardless of whether this cycle started at discovery or on day six of the trip. No component ever talks to another directly — every path runs through the core. Planning doesn't know Sourcing & Booking exists; it only has to know how to talk to the core. That's what keeps four components from becoming twelve pairwise integrations. Monitoring sits apart, drawn at the boundary rather than in the row: it isn't dispatched to like the others, it's subscribed — once, when Sourcing & Booking confirms a commitment — and left running on its own from then on, since a watcher on one flight's status can just as well serve every trip booked on it, not only this one.

Traced — building the first plan
  1. The traveller states intent through the interface: 2 travellers, Vietnam, 7 days, ₹1.5L/person. The core writes it to Desired state and reads Traveller preferences for anything learned from a past trip.
  2. The core dispatches to Planning: build an initial plan from this envelope.
  3. Planning hits a gap it won't guess past — no origin city, no dates — and hands the core a question instead of a plan.
  4. The core can't resolve it from memory, so it surfaces the question to the traveller directly (Inform tier — nothing's committed yet). The traveller answers; the core writes it to Desired state.
  5. The core dispatches to Planning again, now complete. Planning runs its own sequence — see §05 — and hands back a finished plan.
  6. The core reconciles, sets the tier to Confirm — the trip's first real commitment — and surfaces the plan for approval.
Traced — a mid-trip disruption
  1. Monitoring is already listening — it doesn't wait to be asked. It catches BLR→HAN delayed 3h.
  2. Monitoring pushes this to the Reasoning Core as a new trigger — not a response to a request, an interruption.
  3. The core reconciles, classifies the divergence, and dispatches to Planning: devise a revised plan under the new constraint.
  4. Planning hands the revised plan back to the core, which reconciles again, sets the tier, and — per §03 — either proceeds or asks.
05

Inside Planning

Planning has one job: turn Destination + Days + Budget + Travellers into a feasible trip structure. Every trace above treats it as a box that "runs its own sequence" and hands back a plan — here's what that sequence actually does, from a bare traveller request to a validated, day-by-day itinerary.

StepWhat happens
0 · Understand intentSeparate what the traveller said from what has to be inferred. For 2 travellers, Vietnam, 8 days, ₹3L total: destination, duration, party, budget are explicit. Past trips, if any, are read from Traveller preferences first.
1 · What's missing
Hard constraints — missing any one blocks the plan
  • Where you're going · trip duration · budget · who's travelling · origin city
Derived — inferred, never asked
  • Cities / regions — season, budget, party, interests, flight connectivity, travel time
  • Number of bases — modelled, not guessed:
Net trip value = Experience value − Transit cost − Fatigue cost
Bases ≈ Trip duration / (Transit time + 2.5 nights per base)
  • Pace — duration, destinations, party age/composition, activity preference
  • Accommodation type — from budget per person
  • Food preferences — only when stated explicitly
  • Mobility / physical constraints — only when stated explicitly
  • Visa / passport — checked against nationality and destination
  • Weather preference — inferred from origin city
2 · Assemble inputsWith every hard constraint resolved, the working envelope is fixed: Vietnam · 8 days · ₹1.5L/person · 2 travellers.
3 · Understand destinationVietnam decomposes into three regions — geography and climate are regional, not national:
  • North — Hanoi, Ninh Binh, Ha Long, Sapa
  • Central — Da Nang, Hoi An, Hue, Phong Nha
  • South — HCMC, Mekong, Phu Quoc
Each city carries culture, food, nightlife, nature, beach, duration, cost, region — a destination graph, not a flat list.
4 · Coverage potentialEight days maps to several candidate shapes, not one. Every extra destination adds transit time, a transfer, a check-in/out cycle, packing, waiting, fatigue, cost.
  • Plan A — Hanoi + Ninh Binh + Ha Long
  • Plan B — Hanoi + Ha Long + Hoi An
  • Plan C — Hanoi + Hoi An + HCMC
  • Plan D — Hanoi + Ninh Binh + Ha Long + Hoi An + HCMC
5 · Score attractivenessEach destination scores on uniqueness, fit with trip length, seasonality, travel friction, cost. Vietnam has no single climate — October is excellent in the north, risky in the central flood/typhoon zone, only just drying in the south. That alone boosts Plan A/B and downgrades C/D before an activity is chosen.
6 · Score candidate shapesExample: Shape A — a North loop, Hanoi → Ninh Binh → Ha Long Bay → Hanoi; Shape B — North plus Central. Gated first by how many bases the trip can actually support (Step 1's formula), then scored on survivors:
Score = Experience value − Cost − Travel time − Friction
7 · Choose activitiesEvery candidate for the chosen cities, ranked:
Score = Destination importance + Experience quality + Traveller fit + Seasonality − Time required − Cost − Friction − Cluster distance
Survivors are clustered geographically per city, and each tagged anchor, enhancer, or filler — not by this score, but by replaceability: what a day protects last if a disruption forces a cut. Fillers go first; anchors last.
8 · Construct the days
Anchor events — the fixed points a day is built around
  • International/domestic flight · cruise departure · train · a booked timed attraction · hotel check-in/out · restaurant reservation
An anchor event isn't the anchor activity tag from Step 7 — the tag rates replaceability; an event rates nothing, it's just fixed in time, and the day sequences around it.
Constraints checked while sequencing
  • Opening hours · travel time · activity duration (wait time included) · weather · fatigue · meal times · sunset · flight time · security · baggage claim · check-in · booking-slot availability · traveller fit (how much this specific party can absorb, not just what's worth doing)

When it can't proceed

Most of the sequence runs to completion on inference alone. Two things stop it, resolved differently — Planning doesn't know or care which, it just hands the core a question either way.

A hard constraint is missing — no origin city, say. Nothing in memory can supply that; only the traveller can. Duration has no substitute either — a personal choice, always a direct ask. A missing budget number is softer if described qualitatively ("budget-friendly"): the core proposes a figure from benchmark data first, rather than asking cold. Same category of gap, two resolutions, because one has a substitute worth trying and the other doesn't.

Planning needs something another component owns — real routing cost for Hanoi → Hoi An, to score Step 6 instead of guessing. Planning has no supplier access, and isn't allowed to call Sourcing & Booking directly either way — so the question goes to the core, same as any other.

Traced — Planning needs a fact another component owns
  1. Planning reaches Step 6 and needs real routing cost/time for Hanoi → Hoi An — it can't fetch this itself.
  2. Planning hands the core a question, exactly as for a missing hard constraint.
  3. The core dispatches to Sourcing & Booking: retrieve routing options for this hop.
  4. Sourcing & Booking returns the options to the core — not to Planning. Components still never talk to each other.
  5. The core relays the answer to Planning, which resumes Step 6 with real numbers.

Both cases are one mechanism: a component hands back a question, and only the core decides how to resolve it. Planning never learns which.

06

Inside Sourcing & Booking

One job: turn a specific need — this flight, this hotel, this activity — into a secured supplier commitment, fit to whatever is actually scarce in this trip. Not always the cheapest option; whichever one the trip can least afford to be wrong about.

StepWhat happens
0 · Understand the requestSearch only, or search-and-book; which category; against constraints already fixed — dates from an anchor event, budget remaining after Planning's allocation, party size.
1 · Query suppliersPull every candidate matching the ask, from whichever integrations cover this category.
2 · GateThrow out anything breaking a hard rule before scoring: outside the date window, over remaining budget, an unsafe connection, sold out.
3 · Score on scarcityNot a fixed formula — weights are trip-specific. Unconfirmed dates: refundability can outweigh price. No budget headroom: price outweighs a shorter flight. Identical routes can rank differently across two trips.
4 · Flag exposureReports what the autonomy gate needs — price, cancellation policy, decision deadline — but never sets Inform/Confirm/Auto itself. That judgment stays in the core.
5 · ExecuteBook or modify with the supplier; capture the confirmation reference.
6 · Write & subscribeThe booking joins Commitment state; for anything with a status worth watching, this is the moment that fires the one-time subscribe to Monitoring (§04).
7 · VerifyConfirm the supplier's reference actually matches what was asked — right dates, right names — before reporting success.

When it can't proceed

A missing hard requirement (no date window at all) goes to the core, same as any component. The more interesting case runs the other way from §05: Sourcing & Booking sometimes needs something Planning owns — which two cities need connecting is a routing decision, not one to guess at.

Traced — Sourcing & Booking needs a fact Planning owns
  1. Sourcing & Booking is asked for inter-city transport but hasn't been told which leg — Planning's routing (§05, Step 6) isn't confirmed yet at this point.
  2. It hands the core a question rather than guessing at a route.
  3. The core dispatches to Planning: which leg is this, under the shape selected.
  4. Planning returns the leg to the core, which relays it back.

The direction of the question changes; the mechanism doesn't. Every component is, at some point, both asker and answerer — never to each other directly, always through the core.

07

Inside Pre-Trip Prep

One job: confirm the traveller and trip are fit to depart — documents, entry requirements, final logistics — before Day 1 arrives.

StepWhat happens
0 · Read what's fixedDestination(s), nationality if known, dates, party — from Desired and Commitment state, not asked for again.
1 · Document requirementsVisa requirement for this nationality/destination pair, minimum passport validity beyond return, any entry health requirements.
2 · Check held documentsWhere already known — from a past trip's preferences, say.
3 · Gate on blockersA passport expiring inside the validity window, or a required visa not held, goes to the core immediately — it threatens the whole trip, so it doesn't wait its normal turn.
4 · Derive soft-prepOnce documents clear: packing/logistics guidance that depends on the plan — weather, activity types, pickup time. Never blocking, always skippable.
5 · ReconfirmClose to departure: transfer pickup and check-in windows still match Commitment state — a last check, not a re-derivation.

When it can't proceed

Doesn't know nationality or passport expiry — hands the core a question. Same mechanism as Planning's missing origin city: nothing in memory can supply it, only the traveller can.

08

Inside Monitoring

One job: notice, the instant something changes, without being asked. This one reads like a loop, not a step list — the one component that never finishes and gets called again, it just keeps running.

StepWhat happens
0 · Get subscribedWhich bookings to watch arrives once, from Sourcing & Booking's confirmation (§04, §06). A traveller-status signal is different: its own explicit, revocable consent, separate from booking a trip, off by default. Without consent this feed simply doesn't exist for this trip.
1 · Hold the feedA live connection or poll per booking, continuously — and shared: one flight-number watch serves every trip booked on it. A traveller-status feed is the exception: never shared, deleted outright (not paused) the moment consent is revoked.
2 · Detect a changeAgainst last-known status; duplicate pushes from the same event are dropped here, not passed on.
3 · NormalizeA delay, a cancellation flag, a gate change, a location ping — one common shape regardless of source, since that's what the Reconciler reads. Monitoring reports "the traveller is at the airport," never "on schedule" — that interpretation is the Reconciler's.
4 · Push, don't judgeGoes to the core as a new trigger, no opinion attached. Whether a 3-hour delay matters is the Classifier's call, never Monitoring's — the boundary that keeps this component thin enough to be shared infrastructure at all.
5 · Report silence tooA feed gone quiet or erroring gets pushed too — a staleness signal, not nothing. Six hours without a refresh is a different situation than confirmed-on-time, and the core can't tell unless Monitoring says so.
6 · Keep goingThe subscription ends at Post-Trip's close-out, or an outright cancellation — never on its own schedule.

Why there's no "when it can't proceed" here

Every other component can get stuck mid-task because something is waiting synchronously on its answer. Nothing waits on Monitoring that way — it isn't mid-task, it's mid-loop. The closest equivalent is Step 5: it doesn't ask a question, it just says what it knows, including "nothing, currently."

09

Inside Post-Trip

One job: close the loop — confirm what actually happened, reconcile it against what was planned, keep whatever's worth remembering next time.

StepWhat happens
0 · TriggerThe last anchor event completes — a return flight lands, or a timer passes the last planned day.
1 · Gather actualsWhat was actually booked and spent, from Commitment state, against the original envelope in Desired state.
2 · ReconcileCompute the variance and flag anything significantly over or under — a silent log entry isn't reconciliation, a flagged one is.
3 · NotifyA close-out summary to the traveller, Inform tier — nothing left to decide.
4 · Extract preferencesWhich anchors, enhancers, fillers actually got kept, used, or skipped — written to Traveller preferences, built to outlive this trip.
5 · Close task graphEvery task for this trip marked done, Monitoring's subscriptions released.

When it can't proceed

A supplier hasn't finalized billing yet — not a traveller question at all, just an incomplete answer. Post-Trip doesn't escalate it; it waits and retries. Not every stuck component looks like a missing origin city — sometimes there's nothing to ask anyone, only time left to let pass.

10

Stress-tested against scenarios

Everything above is mechanism. Here it is under load — a vague request, a live disruption, and a trivial one — run through the actual loop rather than described in the abstract.

A vague-but-workable request
  1. "A budget-friendly trip to Vietnam from Bangalore in October for 2 people." The core writes what's given to Desired state — destination, origin, party, month — and reads Traveller preferences.
  2. Dispatched to Planning, which flags two gaps: duration is missing outright; budget is only described, not a number.
  3. Duration has no substitute — the core asks directly, Inform tier.
  4. Budget isn't a blind gap, though: the core resolves "budget-friendly" against benchmark data and proposes a figure back for confirmation, Recommend tier, instead of asking cold.
  5. Both settled, Planning proceeds — October's seasonality (§05, Step 5) and the confirmed number now shape scoring exactly as they would have from a fully-specified request.
The same event, two outcomes
  1. Monitoring detects a delay and pushes it as a new trigger — it doesn't decide whether this matters (§08).
  2. The core reconciles the new arrival time against Commitment state and whatever slack the day's construction left around its anchor events.
  3. Slack absorbs it: absorbable. Dispatch to Sourcing & Booking to adjust the transfer — Auto tier, no traveller involved.
  4. The delay eats past a fixed, paid anchor event instead: correctable. Dispatch to Planning, which rebooks around it and keeps the trip's shape intact — Confirm tier, since real money is now on the table even though the plan itself still holds.
A request that needs almost none of this
  1. Traveller asks for dinner at a named place, mid-trip. This never reaches the Classifier — it's a new want added to Desired state, not a divergence from anything.
  2. The core checks that evening against existing anchor events and clustering. No conflict.
  3. Dispatch goes straight to Sourcing & Booking — Planning has nothing to do here this time.
  4. Reservation made, written to Commitment. Monitoring isn't subscribed to it — not everything booked carries the kind of disruption risk worth watching continuously.

Three requests, three different amounts of machinery engaged — because the loop only spends effort where a real question exists.

11

Proven in a working simulation

This is a design validation, not the MVP. The mechanism above isn't only on paper, though — a companion prototype, Dry Run, plays back six scripted scenarios (the three above, plus a passport blocker, a trivial in-trip request, and trip close-out) against three live panels: the traveller, the reasoning core, and whichever component is doing the work, with labeled arrows animating the handoffs between them exactly as described in §04.

Traveller
What the traveller sees — their input, notifications, approval requests.
Reasoning Core
Which loop stage is live — Trigger, Reconcile, Classify, Dispatch, Autonomy Gate — with the relevant Memory snippet updating alongside it.
Component
Whichever of the five is currently invoked, stepping through its own numbered sequence from §05–09 in real time.
Plan a trip
Blind-ask + benchmark-resolved clarification, a cross-component fact fetch, Confirm-tier close.
Flight delay
One trigger, two outcomes — absorbable vs. correctable, toggled live.
Ask for dinner

Trip wrap-up

One deliberate scope choice: Dry Run is a scripted rehearsal, not a live model, and not a build of the product. Every step is authored, not generated — a faithful, repeatable demonstration that the mechanism is internally coherent, not a test of whether a model can reliably reproduce it, and not the MVP itself. Building the real thing — live reasoning, real supplier integrations, the human-gated policy from §12 — is Phase 1 below; this prototype is what happens before that build starts, not a substitute for it.

12

MVP scope & roadmap

Everything defined above is the mechanism. What actually ships first is narrower than that on purpose — every inclusion and every cut below is a deliberate call, not a resourcing accident.

In scope — and why

  • One destination, Vietnam. Depth over breadth — the mechanism has to hold on one real, fully-worked case before it's worth multiplying surface area.
  • The full reasoning core — loop, tiers, Clarification, all three resolution paths. This is the actual differentiator; a partial version can't be tested honestly.
  • All five components, each with a fixed, bounded function set. Depth in defined operations, not a sprawling general-purpose agent.
  • Mandatory human approval on anything with financial exposure, even where the autonomy policy would otherwise permit Auto. Trust is earned in a first release, not assumed.
  • Monitoring scoped to flights, transport, and weather. The highest-frequency, highest-value disruption types; every other supplier feed can wait.
  • Traveller-status (location) tracking is off by default, even where technically available. The same conservatism applied to financial autonomy applies here: a live personal-location feed ships opt-in, consent-gated, and revocable, once, not bundled into the general MVP the way a flight-status watch is (§08).
  • One supplier integration per data type. Prove the mechanism holds against real data before multiplying integrations.

Deliberately out — and why

  • Group trips, divergent preferences. Desired state models one party's wants; a second party's competing wants has no defined reconciliation path yet.
  • Multi-currency, cross-border spend. Commitment state assumes one currency of record — extending it is real design work, not a quick patch.
  • Autonomous spend beyond trivial, reversible actions. A liability and trust ceiling matched to a first release, not a permanent limit.
  • Long-tail failure recovery — lost documents, medical emergencies. Routed to human support; a service problem, not a reasoning one.
  • Live, model-driven reasoning in production. §11's prototype proves the mechanism is coherent enough to demonstrate — it doesn't yet prove a live model reproduces it reliably end to end.
Phase 0 — done
Design validation. Mechanism fully defined (this document) and rehearsed in Dry Run, a scripted simulation (§11). Neither is the product — this phase exists to catch a broken mechanism before a single line of the real system gets built.
Phase 1 — next
The MVP, on probation. The real system, built for the first time: live reasoning, one destination, real supplier integrations. It ships with every tier's trust capped at Confirm — including cases the policy would otherwise call Auto — until live fidelity is actually measured against the rules this document defines. Validation isn't a phase that happens after this one; it's what this phase is for. Nothing acts on trust that hasn't been earned yet.
Phase 2
Earned autonomy. Where Phase 1's logged decisions show the live model actually reproduces the Classifier's and Autonomy gate's judgment reliably, relax that specific tier to its designed level — Auto starts really running autonomously only now, one tier at a time, never by default.
Phase 3
Scope expansion. Additional destinations; a group-trip reconciliation path and multi-currency Commitment state, once the three-state model is extended to support them; the traveller-status feed revisited only alongside a real consent and data-retention design, not before.

What's still open

  • Staleness as its own signal. Monitoring already reports when a feed goes quiet, not just when it changes (§08, Step 5) — but whether staleness itself should shift the autonomy tier, independent of what it's stale about, isn't yet decided.
  • Group trips and divergent preferences. Every component here assumes one Desired state per trip. A travel party that wants different things doesn't have a defined reconciliation path yet.
  • Multi-currency and cross-border spend. Commitment state assumes one currency of record. It bends for a single side-purchase; it isn't yet clear how far it bends before the three-state model needs a fourth dimension.
  • Live reasoning, not scripted rehearsal. §11's prototype proves the mechanism is coherent enough to demonstrate. It does not yet prove a live model reliably reproduces it end to end — that's the natural next validation, not a gap in the architecture itself.
